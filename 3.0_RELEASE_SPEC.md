# Fly Brain 3.0 Release Specification

**Status:** authoritative release definition for 3.0
**Applies to:** `HEAD = 40cf69e` ("Commit accumulated 7X-8N dependencies")
**Established validation:** 1151 passed, 2 warnings, Python 3.10.20

---

## 1. Purpose

This document defines what "Fly Brain 3.0" is, and is the authoritative
release definition for the 3.0 biological-brain and modelling work at
`HEAD = 40cf69e`.

It exists because the repository previously had no authoritative 3.0 release
definition. `3.0D` appeared in exactly one file
(`biological_brain/HH_READINESS_SPECIFICATION.md`, itself superseded), in no
plan or roadmap; `PROJECT_STATE.md` never mentioned 3.0 at all; and
`FLY_BRAIN_2_0_ROADMAP.md` describes a different product direction that
explicitly lists neural networks as a non-goal. Completion could therefore not
be evaluated against any gate.

This document supplies that gate. It records the scope that was implemented, the
scope that is exposed in the product, and the scientific questions that remain
open. It does not create new requirements, resolve open science, or add
product integration.

**Provenance of the requirements below.** Every requirement listed in §3 and §4
corresponds to a module that exists at `HEAD` and a checkpoint that was
implemented and tested. No requirement is stated that is not backed by
repository content. Where the repository records something as unresolved, this
document records it as unresolved and does not convert it into a requirement.

---

## 2. Release Scope

3.0 is the **biological modelling and research architecture** comprising:

1. the 3.0A–3.0C foundation (package, connectome-grounded escape circuit,
   pluggable dynamics, conductance framework, numerical-resolution contract,
   parameter provenance), and
2. the 3.0D work: the 7A–7Z provenance/morphology/passive/electrical/
   action-selection foundation, and the 8A–8N live GFS model.

**3.0 is explicitly not defined as a Discord product release.** The user-facing
product remains the 2.0 behaviour path. This document does **not** retroactively
claim that any 3.0 capability is a Discord user-facing feature. §6 states the
product boundary precisely, and §9 states what "complete" does and does not
mean.

## 5. Completion Criteria

3.0 is complete when **all** of the following hold. These are objective,
repository-checkable conditions. No performance target and no biological
acceptance threshold is introduced.

| # | Criterion | How it is checked |
|---|---|---|
| 5.1 | Every module listed in §3 and §4 exists at `HEAD` | Repository inspection |
| 5.2 | The 3.0D checkpoint test suites pass | `tests/test_biological_brain.py` (3.0D classes) |
| 5.3 | The canonical full suite passes under the established command | `python -m pytest tests/ -q --tb=short --ignore=tests/test_diagnostics.py` |
| 5.4 | Provenance boundaries are preserved | Unresolved records remain `unresolved`; `preferred_side is None`; excluded-quantity counts unchanged; coupling and coupling-refusal entry points still raise |
| 5.5 | Unresolved scientific conflicts remain **unresolved** | 7U and 8G conflicts are not collapsed, and neither is chosen by numerical convenience |
| 5.6 | A clean checkout imports | Fresh `git clone` of `HEAD` imports `biological_brain` and its dynamics modules |
| 5.7 | The GFS demonstration remains isolated from behaviour paths | No behaviour command imports or invokes the adapter; `/scare` semantics unchanged |
| 5.8 | `GFSCircuit` still requires an explicit gap-junction conductance | No default is introduced |

**Explicitly not completion criteria.** Latency agreement with published GFS
values; spike-count agreement; any numeric biological threshold; the GFS
numerical demonstration running end to end; any Discord-visible output from
3.0D.

## 6. Product Boundary

This section is part of the release definition. It states the product state
exactly, so that "3.0 modelling complete" is not read as "3.0 product
integrated".

| Path | User-reachable today? | State |
|---|---|---|
| **2.0 behaviour** (`GroupBrain`) | **Yes** — 24 slash commands | The primary and only user-facing behaviour path |
| **3.0B `BiologicalBrain`** | **No, by default** | 19 commands reach `biological_brain.step()` structurally, but only when `biological_mode != LEGACY_2_0` **and** the circuit flag is enabled. Both default off (`LEGACY_2_0`; all `BIOLOGICAL_CIRCUITS` `False`). Additionally, `snapshot["biological_signals"]` is produced but **never read** by `fly_bot.py`, `brain_dashboard.py` or `dashboard_animation.py`, so enabling it currently changes nothing a user sees. |
| **3.0D GFS** | **No** | Library-only. No Discord command, experiment, or dashboard path reaches it. `gfs_demonstration_config` defaults to `None` and is deliberately stored-but-unconsumed. |
| **Developer / research experiments** | **Yes — `/experiment`** | Bounded (`steps` 1–120, `trials` 1–10), returns a summary, runs off the blocking path. Covers `habituation, sensitization, phototaxis, competing_drives, social`. **Does not reach 3.0D.** |

The GFS numerical demonstration is a **developer/research fixture**. It is
driven by an explicit numerical GF event
(`GFEventSource.DIRECT_NUMERICAL_STIMULUS`) and an explicitly declared
gap-junction conductance whose provenance must state that it is not a biological
value. It is not a sensory prediction and must not be presented as one.

## 7. Scientific Limitations and Explicit Non-Requirements

Each row is **not** an implementation requirement. Incomplete or unresolved
does not imply required.

| Item | Status | Meaning |
|---|---|---|
| **7U gap-junction unit conflict** | **Unresolved science** | Paper states 135 µS (young) / 34.5 µS (old); the compiled ModelDB source executes 135 nS / 34.5 nS. Exactly 1000×. `preferred_side is None`. A resolution requires source evidence, not numerical preference. |
| **8G PSI→DLMn peak conductance** | **Unresolved science** | Paper 80 µS (estimated) vs ModelDB source weight 0.08, exactly 1000×. Recorded unresolved. Selecting a branch by which value makes the simulation stable or spike is explicitly forbidden. |
| **8I sensory → live-GF coupling** | **Intentionally unsupported** | No source provides a conductance, reversal potential, current, receptor kinetic, release probability or density for LC4→GF or LPLC2→GF. `couple_to_live_gf()` and `run_looming_through_live_circuit()` raise by design. von Reyn 2017 locates the linear integration *within the GF cell*, so the conversion is a property of GF membrane dynamics, not a function of the stimulus. |
| **8N escape probability** | **Intentionally unresolved** | Always `None`, status always `"unresolved"`, `escape_guaranteed` always `False`, `parallel_pathways_exist` always `True`. Per Chai 2025, GF activity biases action selection while parallel non-GF escape pathways exist; a GF action potential is not guaranteed escape. Enforced by raising constructors. |
| **Q10** | **Excluded, non-required** | Absent from all cited sources; listed among the 7V excluded quantities. Its absence is recorded, not tasked. |
| **LC4/LPLC2 → GF kinetics, release probability, receptor density** | **Excluded, non-required** | No source states them. 7V retains 14 excluded quantities; 7Y retains 13 unavailable sensory quantities, none resolved. 8M records the connection as anatomically and functionally established but quantitatively unresolved. |
| **8K GF-fired-but-no-motor-output** | **Observed edge state, no documented requirement** | 8K can raise when a GF action potential is detected but no motor-neuron action potential is observed within the window. No specification, test, or design note requires representing this state. Recorded here so it is not mistaken for a defect. |
| **Emotion-by-emotion GFS integration** | **Excluded, non-required** | No repository document maps Discord commands or emotions to GFS pathways. `FLY_BRAIN_2_0_ROADMAP.md` is a 2.0 product document that explicitly lists neural networks as a non-goal, and is not a 3.0 authority. |

**Further non-goals.** This document does not claim that the model is a
complete *Drosophila* brain, that it models every sensory pathway, or that it
reproduces behaviour quantitatively. Those are neither implemented nor
required here.

## 9. Release Interpretation

**"3.0 complete" means the documented 3.0 biological modelling scope in §2–§4 of
this specification is implemented and validated at the specified checkpoint, and
the conditions in §5 hold.**

It does **NOT** mean any of the following:

- all biological questions are solved;
- all scientific ambiguities are resolved (7U, 8G and 8I remain open by design);
- all biological signals are rendered in Discord (§6: 3.0B signals are not);
- the GFS is exposed as a user-facing Discord behaviour (§6: it is not);
- the model is a complete *Drosophila* brain;
- every possible sensory pathway is modelled;
- the escape model reproduces measured GFS or muscle latencies.

A reader may state that 3.0 is complete only with that qualifier attached.

## 10. Future Work Boundary

Three categories, deliberately kept separate. **None of these is part of the
3.0 release**, and none becomes part of it unless this document is explicitly
revised.

**Product integration work** (engineering, no new biology)
- Render `biological_signals` in Discord responses or the dashboard.
- Decide whether and how to expose a research surface for the GFS numerical
  demonstration (the existing `/experiment` path is the natural candidate).
- Decide whether `BIOLOGICAL_CIRCUITS` should ever default on.

**Future biological research** (new modelling)
- LC4/LPLC2 → GF synaptic kinetics, if and when a source supplies them.
- Long-mode escape, motor output, neuromuscular junction, muscle.
- A sensory-to-live-GF coupling, which would require 8I's boundary to be
  resolved rather than bypassed.

**Scientific-resolution work** (research, not engineering)
- 7U: determine the intended unit of `g_gap` from primary sources.
- 8G: determine the intended unit of the PSI→DLMn peak conductance.
- 8I: determine whether a source-backed sensory coupling exists at all.

## 11. Change Control

This file is the authoritative 3.0 release definition.

- Additions to 3.0 scope must be made as an **explicit edit to this document**,
  together with the implementing module and its tests. Scope must never be
  inferred from a checkpoint prompt, a conversation, or the existence of code.
- Removing a boundary — for example resolving 7U or 8G — is a change to this
  document and to the implementing module, and requires source evidence.
  Numerical convenience is not evidence.
- Renumbering or superseding this document should record the revision and the
  `HEAD` it was written against.
- Where this document and a checkpoint implementation disagree, the
  implementation is authoritative for behaviour and this document must be
  corrected; the disagreement itself is a defect to be recorded.
